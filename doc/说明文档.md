# Loom · AI 页面工坊 方案说明

> 文档日期：2026-11-26  
> 对应代码：当前工作区 `d:\bishidemo` ，采用VS code+claude code开发模式，claude code大模型对接deepseek
> 定位：面向演示交付的 Prompt-to-Prototype 应用，不是商业级 AI 全栈平台

## 1. 项目目标

用户输入一句自然语言需求，系统调用 DeepSeek 生成：

1. 一个完整、可交互、可独立运行的单文件 HTML 页面；
2. 一份配套后端代码，语言优先遵循用户需求，未指定时默认 Java；
3. 前端在线预览、源码查看、历史记录和点选修改能力；
4. 赛马模式下的两种设计风格对比与择优保留；
5. 大模型不可用时的可交互 Mock 兜底。

当前版本重点验证“需求 → 生成 → 预览 → 验收 → 修改 → 入库”的完整演示链路，而非生产级全栈托管平台。

## 2. 功能地图

| 模块 | 当前实现 |
| --- | --- |
| 普通生成 | 原始用户提示词直接发给 DeepSeek，不附加风格限制 |
| 后端语言 | 自动识别 Python、Node.js、Go、PHP、C#、Ruby、Rust、Kotlin、Java；默认 Java |
| 生成进度 | 需求规划 → 生成中 → 测试 → 验收 → 完成，成功后自动收起 |
| 预览 | iframe `sandbox="allow-scripts"` |
| 源码 | 前端 HTML / 后端代码切换查看 |
| 历史记录 | PostgreSQL 持久化、重新打开、删除、下载 ZIP |
| 赛马模式 | 庄重内敛 / 活泼艳丽两种风格并行生成，左右对比，选择其一入库 |
| 在线修改 | 预览中点选元素，输入修改建议，调用模型重写完整 HTML |
| Mock 兜底 | 无 Key、接口异常、超时、格式异常时返回可交互加法计算器 |
| 部署 | Render、阿里云 ECS（公网 IP 直连 Gunicorn） |

## 3. 总体架构

```text
┌──────────────────────────────────────────────────────────────┐
│ 浏览器：原生 HTML + CSS + JavaScript                          │
│ 输入框 / 进度条 / 预览 iframe / 源码面板 / 历史记录 / 修改弹窗  │
└───────────────────────────────┬──────────────────────────────┘
                                │ Fetch JSON + CSRF Token
┌───────────────────────────────▼──────────────────────────────┐
│ Django 4.2                                                   │
│  ├─ generator.views：页面、生成、选择、修改、删除、下载        │
│  ├─ generator.services：Prompt 编排、DeepSeek、Mock、校验      │
│  └─ generator.models：GenerateHistory                        │
└───────────────┬──────────────────────────────┬───────────────┘
                │                              │
        ThreadPoolExecutor                Django ORM
                │                              │
┌───────────────▼─────────────┐   ┌────────────▼───────────────┐
│ DeepSeek OpenAI 兼容接口     │   │ PostgreSQL（主应用数据库）  │
│ /chat/completions            │   │ GenerateHistory             │
│ 30 秒超时                    │   │ 异常时本地可回退 SQLite     │
└───────────────┬─────────────┘   └────────────────────────────┘
                │
         失败/无 Key
                ▼
┌──────────────────────────────────────────────────────────────┐
│ Mock 加法计算器（普通模式中性版 / 赛马两套风格版）             │
└──────────────────────────────────────────────────────────────┘
```

关键边界：

- 主应用的 PostgreSQL 只保存生成记录。
- 大模型生成的后端代码不会自动运行，也不会自动连接主应用的 PostgreSQL。
- 生成的 HTML 只在浏览器沙箱中运行，服务器不执行生成代码。

## 4. 为什么选择 Django

需求本身锁定了 Django 4.2，但在实现层面它仍然适合这个项目：

### 4.1 开发效率

- 自带 ORM 和迁移系统，`GenerateHistory` 的建表、查询、倒序展示、删除只需很少代码。
- `dj-database-url` 可以直接消费 Render、阿里云 RDS 等平台提供的 `DATABASE_URL`。
- 模板 + JSON API 的组合足以完成当前单页应用，不需要额外搭建 SPA 工程链。
- 单项目、单 app 的结构便于笔试验收和快速部署。

### 4.2 安全基础

- 自带 CSRF Middleware，所有写操作都要求 CSRF Token。
- 模板自动转义，历史记录和提示词通过 `json_script`、`textContent` 渲染，避免直接拼接用户内容。
- 静态文件和用户生成内容不在服务端执行，生成 HTML 只放入受限 iframe。
- 环境变量读取、密钥管理和部署配置可以集中到 `settings.py`。

### 4.3 运维成本

- WSGI + Gunicorn + systemd 即可在单台 ECS 上运行。
- 不引入 Redis、Celery、消息队列和独立前端服务，部署依赖少。
- 单数据库连接配置同时适配本地 SQLite、Render PostgreSQL 和阿里云 PostgreSQL/RDS。

### 4.4 为什么不用 FastAPI/Flask/Node

- FastAPI/Flask 更轻，但需要额外选型 ORM、迁移、CSRF、模板和后台管理方案；对本项目会增加交付复杂度。
- Node 需要额外前端/后端构建链和运行环境，不符合“原生 HTML + JS、少依赖”的要求。
- Django 的“电池齐全”对这类小体量、强表单/数据库交互的演示应用更直接。

### 4.5 Django 带来的限制

- 当前生成请求是同步长请求，最长约 30 秒；高并发时会占用 Gunicorn worker。
- 没有异步任务队列、流式输出、取消任务和任务重试。
- 没有 WebSocket/SSE，进度条中的测试、验收阶段是前端展示，不是服务器真实阶段。
- 若演进成生产平台，应增加 Celery/Redis 或专门的任务服务。

## 5. 数据模型

`GenerateHistory` 位于 `generator/models.py`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BigAutoField | 主键 |
| `prompt` | TextField | 原始用户需求 |
| `html_code` | TextField | 前端完整 HTML |
| `backend_language` | CharField(32) | 后端语言标识 |
| `backend_code` | TextField | 后端代码 |
| `created_at` | DateTimeField | 创建时间，倒序排序 |

题目原要求是 `prompt`、`html_code`、`created_at` 三个字段；额外增加 `backend_language` 和 `backend_code`，用于“查看源码”和 ZIP 下载。否则后端代码无法持久化，刷新历史后也无法查看。

## 6. 核心流程

### 6.1 普通生成

1. 浏览器提交 `{ prompt, race_mode: false }` 到 `POST /api/generate/`。
2. 后端识别用户是否指定后端语言，未指定使用 Java。
3. 使用 `ThreadPoolExecutor` 并行执行两个调用：
   - 前端 HTML 生成；
   - 后端代码生成。
4. 前端系统提示词固定为：

   ```text
   你是前端工程师，只输出完整可独立运行的单文件HTML，里面JS可以交互，不要额外解释、不要markdown代码块标记。
   ```

5. 普通模式不添加任何风格提示词，用户原始需求原样传入。
6. 后端代码使用独立的后端 system prompt 生成，避免破坏前端固定提示词。
7. 对模型返回做 Markdown 代码围栏清理、HTML 完整性检查和异常兜底。
8. 写入 `GenerateHistory`，返回记录和源码。
9. 浏览器展示预览、源码、历史记录。

### 6.2 赛马生成

1. 基于同一原始需求构造两个用户提示词：
   - 庄重内敛：正式、沉稳、有秩序感，使用藏蓝/酒红/墨绿/深棕等有成体系的色彩，禁止黑白灰。
   - 活泼艳丽：高饱和鲜明配色、渐变、圆润元素和适度动效。
2. 两个 HTML 请求并行，另有一个共享后端代码请求并行。
3. 两个候选先不入库，只在浏览器展示。
4. 用户点击“保留此方案”后，调用 `POST /api/select/` 将所选方案写入数据库。
5. 另一方案从界面消失，不保存。

### 6.3 点选修改

1. 用户点击“点选修改”。
2. 前端向 iframe 注入的桥接脚本发送 `postMessage`，进入元素选择模式。
3. 用户点击页面元素，桥接脚本把标签、文字、CSS 选择器发回父页面。
4. 父页面弹出修改对话框，提交当前 HTML、修改建议、元素信息和记录 id。
5. 后端调用模型重写完整 HTML，成功时更新记录。
6. 失败时返回原 HTML 和提示，不破坏当前预览。

### 6.4 Mock 兜底

以下情况均返回可交互加法计算器：

- `LLM_API_KEY` 为空；
- 请求连接失败、超时、HTTP 非 2xx；
- 返回非法 JSON、空内容；
- 返回内容不是完整 HTML。

普通模式使用中性 Mock，赛马模式分别使用庄重内敛和活泼艳丽的 Mock。记录仍正常入库。

## 7. API 一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 页面和历史记录 |
| POST | `/api/generate/` | 普通或赛马生成 |
| POST | `/api/select/` | 保存赛马选中的方案 |
| POST | `/api/revise/` | 点选元素后的自然语言修改 |
| POST | `/api/history/<id>/delete/` | 删除记录 |
| GET | `/api/history/<id>/download/` | 下载 HTML + 后端代码 ZIP |

所有 POST 请求使用 Django CSRF 校验；删除和下载接口按记录 id 操作。

## 8. 前端实现

- 使用原生 HTML/CSS/JS，无 Vue/React，无构建步骤。
- 预览 iframe 使用 `sandbox="allow-scripts"`，不开启 `allow-same-origin`。
- 通过 `postMessage` 与 iframe 内部的编辑桥接脚本通信。
- 沙箱禁止访问真实 `localStorage`，预览前注入内存版 `localStorage/sessionStorage` shim，避免生成页面因 `SecurityError` 整页失效。
- 历史记录、源码输出使用 `textContent` 或 `json_script`，不直接拼接不可信 HTML。
- 进度条在生成成功约 1 秒后淡出；失败时保留错误状态。
- 历史删除、下载在生成期间仍然可用；删除当前预览记录时，若生成仍在进行则保留加载界面。
- ZIP 包包含 `index.html` 和 `backend.<扩展名>`；后端代码为空时不添加后端文件。

## 9. 安全与可靠性

### 已实现

- 密钥只从 `.env` / 环境变量读取，`.env` 已加入 `.gitignore`。
- 大模型 Key 不写入源码、模板或仓库。
- 所有 POST 操作有 CSRF 校验。
- 生成 HTML 在沙箱 iframe 中运行，不能访问父页面 Cookie、DOM 和存储。
- 生成内容不会在 Django 服务端执行。
- 30 秒模型超时；异常自动 Mock。
- Gunicorn 部署建议 `--timeout 90`，大于模型超时。
- 删除、下载接口使用数据库 id 查询，不拼接文件路径。
- 下载文件名固定为 `loom-history-<id>.zip`，ZIP 内部文件名固定，避免路径穿越。

### 当前不足

- 没有用户认证、权限和租户隔离；任何能访问页面的人都可删除、下载记录。
- 没有接口限流，公网暴露时可能被刷 DeepSeek 额度。
- ECS 直连方案默认是 HTTP，没有 HTTPS。
- 没有对生成 HTML 做安全审计；沙箱是主要隔离手段。
- 没有审计日志、监控、告警和自动备份。
- 生成代码质量依赖模型，非确定性较强。
- “测试 / 验收”进度阶段是前端展示，不是真实自动测试。

## 10. 赛马功能设计与局限

### 10.1 当前设计

赛马模式是“同模型、双风格提示词”的并行生成：

- 两个 HTML 请求使用同一 DeepSeek 模型；
- 风格由追加的用户提示词控制；
- 后端代码只生成一次，两个候选共享；
- 用户手动选择；
- 选中后入库，落选方案不保留；
- 刷新页面会丢失尚未选择的候选。

### 10.2 局限

1. **不是真正的多模型赛马**：没有跨模型、跨代理团队的并行比较。
2. **没有客观评分**：没有自动质量评分、自动测试或盲评，完全依赖用户主观选择。
3. **没有自动运行测试**：进度条中的“测试/验收”是界面状态，不是服务器实际执行测试。
4. **前后端未联调**：生成的 HTML 和生成的后端代码只是两份文本，不会自动启动后端，也不会自动接入。
5. **后端共享**：后端代码只生成一份，不随两个视觉方案分别变化。
6. **候选不持久化**：选择前刷新或离开会丢失两个候选。
7. **没有多轮迭代选择**：不能多次生成后横向比较更多方案，也没有合并能力。
8. **风格指令可能与用户原始风格冲突**：赛马模式强制追加风格，用户原提示词中的风格会被覆盖或混合。
9. **资源成本较高**：一次赛马产生两个 HTML 请求和一个后端请求，可能触发模型限流或耗时增加。
10. **预览兼容性有限**：沙箱环境禁止真实持久化存储和跨域后端调用，部分生成页面在预览中仍可能受浏览器 API 限制；当前只针对 `localStorage/sessionStorage` 做了兼容层。

### 10.3 改进方向

- 接入多个模型或多个 Agent；
- 后端静态检查 + 浏览器自动化测试；
- 自动评分和盲选；
- 持久化两个候选及评分；
- 将“测试 / 验收”改成真实流水线状态；
- 支持合并两个方案。

## 11. 与 atoms.dev 的对比

> Atoms 是持续迭代的商业产品，以下信息基于其官网公开页面、Neon 官方发布文章及其他公开资料（检索日期：2026-11-26）。具体功能和定价以 atoms.dev 官方为准。

### 11.1 Atoms 的公开定位

公开资料显示，Atoms 是 DeepWisdom 推出的 AI 原生多代理平台，目标不是单页生成，而是用“AI 团队”完成从调研、产品规划、架构、编码、测试到上线的全栈产品交付。其公开能力包括：

- 多代理协作：研究、产品经理、架构师、工程师、测试、SEO、投放、数据分析等角色；
- 全栈生成：前端、后端、数据库、认证、支付、部署；
- Atoms Cloud：托管后端、Neon PostgreSQL 数据库、认证、存储、密钥和 AI 模型接入；
- Race Mode：跨多个模型或 Agent 团队并行构建方案，并进行评分/选择；
- 可视化编辑、代码导出、GitHub 同步、一键部署和自定义域名；
- 商业订阅与 credits 计费。

### 11.2 核心差异

| 维度 | 本项目 | atoms.dev |
| --- | --- | --- |
| 产品定位 | 单页 Prompt-to-Prototype 演示 | 商业化全栈产品构建平台 |
| 生成编排 | 单模型、单次 Prompt、并行双风格 | 多 Agent 协作、研究/规划/架构/开发/测试/增长 |
| 前端 | 单文件 HTML，iframe 预览 | 完整应用界面，可视化编辑器 |
| 后端 | 生成代码文本，不自动运行 | 自动生成并运行后端服务 |
| 数据库 | 主应用 PostgreSQL；生成后端未强制数据库 | 每个应用独立 Neon PostgreSQL 实例 |
| 认证/支付 | 无 | 内置认证、Stripe 支付等能力 |
| 部署 | 手动部署 Render/ECS | 一键托管、域名和发布 |
| 赛马模式 | 同一模型两种风格，人工选择 | 多模型/多 Agent 并行，自动评分与择优 |
| 测试验收 | UI 展示进度；少量静态校验 | 宣称有测试工程师参与构建与质量验证 |
| 在线修改 | 点选元素 + 自然语言，整页重写 | 可视化编辑 + 代码级修改 + 迭代 |
| 代码导出 | ZIP 下载 | 代码导出、GitHub 同步 |
| 多用户/多租户 | 无 | 平台化用户、项目、计费、隔离 |
| 计费 | 自建，模型成本自付 | credits 订阅 |
| 运维 | 单实例自运维 | 托管云服务 |

### 11.3 本项目的具体不足

1. **工作流深度不足**：没有需求研究、产品规划、架构设计、自动测试等 Agent 流水线，只有一次生成调用和一次修改调用。
2. **全栈闭环不足**：后端代码不运行，生成页面与后端不联调；这更接近“原型代码生成器”，而不是可上线应用。
3. **数据库能力不足**：主应用有 PostgreSQL，但生成后端没有默认数据库设计、迁移、连接注入和数据持久化保证。
4. **赛马能力不足**：只有同模型双风格，没有跨模型质量比较、自动评分和批量候选管理。
5. **自动质量保障不足**：没有自动化浏览器测试、接口测试、无真实测试阶段；生成结果存在不可控的 JS/CSS 错误风险。
6. **产品化能力不足**：没有登录、权限、限流、计费、团队协作、项目空间、托管域名、监控和审计。
7. **编辑能力不足**：点选修改是整页重写，不是局部差异修改；复杂页面可能发生结构漂移。
8. **扩展性不足**：长请求直接占用 Web worker，没有队列、取消、重试和任务恢复。
9. **多租户与安全隔离不足**：没有用户级数据隔离，公开访问时任何用户都可能操作历史记录。
10. **生态和集成不足**：没有 GitHub、支付、认证、云数据库、部署流水线等集成。

### 11.4 本项目的相对优势

- 代码量小、结构透明，便于面试演示和二次改造。
- 可完全自托管，无平台锁定，密钥和数据自己掌控。
- Prompt 固定、行为可解释，Mock 链路保证演示不中断。
- 依赖少，Render 或单台 ECS 即可运行。
- 无订阅成本，只承担 DeepSeek API 费用。
- 适合作为 Prompt-to-Prototype、LLM 兜底、沙箱预览和赛马交互的教学/演示样本。

## 12. 后续演进建议

按优先级建议：

1. **上线前安全**：认证、限流、HTTPS、按用户隔离历史记录、API 额度控制。
2. **真实任务化**：将生成改为异步任务，使用 SSE/WebSocket 展示真实阶段，支持取消和重试。
3. **后端闭环**：为生成后端注入数据库，生成迁移/初始化脚本，并提供一键启动或托管运行。
4. **质量保障**：HTML/JS 静态校验、浏览器自动化交互测试、接口冒烟测试。
5. **赛马升级**：多模型、自动评分、盲评、候选持久化与方案合并。
6. **编辑升级**：按选择器做局部 diff 修改，减少整页重写。
7. **产品化**：用户体系、项目空间、GitHub 导出、部署托管和审计。

## 14. 结论

当前实现是一个边界清晰、可运行、可演示的 Django Prompt-to-Prototype 应用。它完整覆盖了题目要求的主链路，并具备大模型异常兜底、沙箱预览、历史持久化和双风格赛马能力。

但它不是 atoms.dev 的替代品，也不应当被描述为生产级 AI 全栈平台：缺少多 Agent 编排、生成后端运行与数据库、自动测试、认证、计费和托管能力。更准确的定位是“可自托管的 AI 原型生成工作台”。
